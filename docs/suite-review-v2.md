## Harness validity and failure interpretation

The earlier harness review led to all-file installed-package provenance verification, valid seed overrides, bounded semantic reducers, explicit browser unrun identifiers, nonrecursive result aggregation, direct disposal assertions and a working fresh default candidate preparation. Those corrections are documented in `suite-review.md`. The second challenge review removed a weak shared-cache stress oracle that had used unique URLs, strengthened buffered cancellation to follow an observable pending-body phase, and distinguished the original merged baseline from the current pinned PR candidate.

The review-to-test aggregator binds observed TAP/compiler/browser records to the candidate commit, installed package-content digest and suite-input digest, and rejects skipped/cancelled Node evidence. Missing browser IDs remain `not-run`; planned IDs are not counted as observed executions. Its selectors map named observations rather than independently proving the quality of an assertion. The complete runtime and release gates remain separate requirements.

Several details matter when interpreting future results:

- **Use independent oracles.** Avirx build, preview, cURL and dispatch may share a defect. Compare wire paths/bytes with explicit expected values or native requests, and compare HTTP semantics with a fixture that actually distinguishes them.
- **Avoid vacuous assertions.** No observed destination request is meaningful only if a positive-control path reaches that destination. Cache generation assertions need an otherwise eligible response. A private/authenticated response that never caches cannot establish generation correctness.
- **Keep phase checks observable.** Deferred gates, response hooks, queue diagnostics and server close events are stronger than short fixed sleeps. Scheduler stalls can cause timing failures without indicating a product regression; preserve logs and identify harness versus contract failures before rerunning.
- **Keep failures visible.** Invalid input, callback rejection and operation errors have different owners. Catching any exception is suitable only where the public contract promises rejection without specifying its class; stable error kinds and original cause identity should otherwise be asserted.
- **Do not count fixture success as a product assertion.** A successful server startup, browser launch or package install supplies the test environment. It does not establish the feature being tested.
- **Preserve counterexamples.** Keep original seed and fixture, the assertion difference and reduced fixture where applicable. A reducer failure is a harness problem and must not erase the original mismatch.

The final aggregate also requires an engine-level passed status and no cleanup errors before browser IDs can satisfy a row. A browser with all feature assertions passed but failed cleanup therefore fails both the browser lane and its review rows.

## Publication privacy review

It found no real credential/private-key or nonpublic dependency evidence. Authentication strings in tests are explicit fake fixture values. Dependency resolution uses the public npm registry; source links are public GitHub URLs, and requests use loopback or reserved invalid hostnames.

The first scan found a recorded browser-launch failure containing machine-local paths. The owner sanitized the affected recorded results throughout both reachable commits. A second audit at `c1d5e19cf2ccd4a17a74601f17bff25c755b3255` found no remaining private local paths or real credential evidence in the tracked tree or 33 unique reachable blobs. Only three recorded JSON files changed in that sanitization; test and source code were preserved. This document deliberately avoids reproducing the original paths. The privacy review is scoped to repository content and reachable history. It does not claim remote erasure of unreachable objects or third-party caches after a history rewrite. Rewritten history and deleted runs are not a guarantee of remote object erasure. Visibility and history operations remain with the owner. Recheck newly recorded results, and sanitize raw diagnostic paths before committing public evidence.
